# Standing rule — no AI language in anything a customer reads

**Set 13 October 2026, by the director, after reading the What We Offer page.**

> "Noone in construction will buy a service generated by AI, this is a very
> sceptical industry."

He is right, and the reasoning matters more than the rule. A Project Director
deciding whether to hand over the site establishment is not buying software. He
is buying somebody who will answer the telephone when the welfare has not
arrived and the crew is standing in a field. Copy that says a document was
*assembled by a named agent* tells him there is nobody to ring.

## The rule

**Nothing a customer, a buyer, a bid evaluator or a supplier reads may describe
ETABLIX work as produced by AI, by an agent, or by a machine.** That covers the
website, the Diagnostic, bid returns, prequalification answers, letters, emails,
LinkedIn, adverts and the blog.

Banned in customer-facing copy: *AI, A.I., artificial intelligence, AI-native,
AI-powered, AI-generated, agent, AI agent, agentic, LLM, machine learning,
generative, autonomous, copilot, neural, chatbot,* and *assembled / produced /
written by machine*.

Also banned as a near-synonym a sceptic will read the same way:
**intelligence layer**.

**Not banned, because they are not AI claims.** *Automated* in its ordinary
sense — bot protection on a form, automatic deletion of a file, an automated
cross-check. *Execution intelligence*, *scenario intelligence* and
*construction intelligence* are ordinary portfolio-reporting vocabulary and read
as dashboards, not robots. They are listed here so the next person sweeping the
site knows they were considered and kept.

## What replaces it

Not a euphemism. The true statement, which is stronger:

| Instead of | Say |
|---|---|
| assembled by a named agent | produced and signed off by the construction professional accountable for it |
| reconciled by machine | cross-checked line by line before the pack can be issued |
| produced by a named agent inside an approval boundary | one named person accountable for the stage, and nothing leaves it until they approve |
| construction AI operating system | construction project control platform |
| the AI writes the report | the report presents those findings and cannot recompute them |
| none with an AI-native control platform | few who will take the whole site environment as one accountable scope |
| AI forecasting | forecasting |
| run an AI agent | run an automated check |
| one intelligence layer | one control layer |

**The trust argument survives the rewrite intact.** The old CONSTRUX bullet
argued that sixteen deterministic engines produce the findings and the write-up
cannot recompute them. That is a good argument. It is a *better* argument with
the technology label removed, because what the buyer actually wanted to know was
whether a number in the report can be followed back to a clause and a document.
So the bullet now ends: *if a number in a CONSTRUX report cannot be followed to
its source, it does not get printed.*

## What is not a claim about the service

- `robots.txt` naming GPTBot, ClaudeBot and the other retrieval crawlers. That
  is crawler configuration, it is not read by a buyer, and it is deliberately
  permissive so answer engines can find the site. Leave it alone.
- `llms.txt`, the plain-text site map for answer engines. Same reason.
- Internal engineering files, test suites, deployment runbooks and this
  repository's own documentation. Nobody is sold to from a runbook.

## The one thing deliberately left undone

The VERYX Platform API still publishes `GET /agents`, `POST /agents/{type}/run`
and the scopes `read:agents` and `run:agents`. Those are real identifiers in a
machine contract, defined in `backend/lib/store.js`, `backend/lib/veryx.js` and
`backend/routes/veryx-public.js`, asserted by the test suite, and possibly
already integrated against. Renaming them is a breaking API change and belongs
in its own deliberate decision, not in a copy sweep. **Every human-readable
description around them has been rewritten** — the table now says *automated
check*, not *AI agent*. If the identifiers are to change too, that is a separate
piece of work across the backend, the docs and the tests, with a deprecation
window.

## The blog post

`ai-agents-in-construction` is unpublished, not deleted. Its entry was removed
from `content/blog/schedule.json`, which by the blog system's own design excludes
a post from the index, the sitemap, the feed, llms.txt and every related-post
block. The source stays in `content/blog/`. The generated page was removed so
the URL no longer answers.

It was the strongest AI signal on the site — the card described running thirteen
AI agents inside a live construction business — and it sat two clicks from the
offer. The argument inside it is sound, but a sceptical buyer searching for
ETABLIX would have found it before finding anything about site establishment.
One line in the schedule file puts it back if that judgement ever changes.

## How to check this stayed true

    cd frontend/public && grep -rnoiE \
      '\bA\.?I\b|artificial intelligen|agentic|machine learning|\bLLM\b|GPT|autonomous|copilot|neural|generative|chatbot|AI-native|AI-powered|intelligence layer' . \
      | grep -vE 'robots\.txt|meta name="robots"'

Empty output is the pass. Run it before any site deployment. The only expected
hits anywhere are the VERYX API identifiers above and the crawler configuration.
